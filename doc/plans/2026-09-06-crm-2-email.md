# CRM-2 (Email-behúzás) — kivitelezési terv

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Gmail levelei ügyfélhez kötve landolnak a CRM idővonalán — determinisztikus hozzárendeléssel, és ahol az nem biztos, ott emberi megerősítéssel, ami egyben tanít is.

**Architecture:** A `gmail` extension `mailbox` szerződését fogyasztjuk `consumes`-szal. A söprés a szerződésen át listáz és olvas, majd `recordEvent`-tel ír — idempotensen, a `UNIQUE(source_system, source_id)` indexre bízva. A hozzárendelés **tiszta függvény**, külön fájlban, táblázatos teszttel. Ami nem biztos, az a besorolatlan sorba megy, és az operátor egy kattintása rendeli hozzá — ugyanaz a kattintás tanulja meg a címet.

**Tech Stack:** Node ESM, `node:test`, `node:sqlite` (teszt), a CRM-1-ben lefektetett repo és rpc rétegek.

**Forrás-spec:** `doc/specs/2026-09-06-crm-extension-design.md` (3.3–3.4 és 12. fejezet)
**Előzmény:** `doc/plans/2026-09-06-crm-1-mag.md` — lezárva, main-re merge-elve

## Global Constraints

- **A DB-mezőnevek angolul.** A felület és a kommentek magyarul.
- **A `setup(ctx)` szinkron, idempotens, csak a `state`-et tölti.** Se timer, se listener — a host minden reloadkor újrahívja. **A söprést nem időzítő hajtja**, hanem hívás (rpc a lapról, tool az ügynöktől).
- **Az extension nem importálhat a host `src/`-jéből.**
- **Minden behúzás idempotens**: `recordEvent` és `recordUnmatched` az `ON CONFLICT DO NOTHING` + visszaolvasás mintát követi, ami a CRM-1-ben már áll. Egy söprést kétszer lefuttatni ingyenes.
- **A hozzárendelés soha nem hív LLM-et.** (spec 1.2) Ez a fázis egyetlen modellhívást sem tesz.
- **Az idegen szöveg adat.** A levél tárgya és törzse soha nem kerül promptba adatként való megjelölés nélkül, és soha nem értelmezzük utasításként.
- **Nevesített hibák**, üres válasz helyett: `crm_*` kódok, ahogy a CRM-1-ben.
- **A lint-baseline kiadási kapu**, net-új ujjlenyomat nélkül. `lint:baseline:update` tilos.

## Amit a CRM-1-ből örökölünk, és ellenőrizve van

A `gmail` `mailbox` szerződése, ahogy a kód ma áll (`extensions/gmail/src/contract.mjs`):

| | |
|---|---|
| Név / verzió | `MAILBOX_CONTRACT = 'mailbox'`, `MAILBOX_CONTRACT_VERSION = 1` |
| Metódusok | `mailbox`, `labels`, `list`, `get`, `draft`, `outbox` |
| `list(args)` | `{ labelIds, q, max, cursor }` → `{ ids, nextCursor, complete, stoppedOn }` |
| `get({ id })` | tíz mező: `id`, `threadId`, `labelIds`, `subject`, `fromName`, `fromEmail`, `sentAt`, `text`, `textInAttachment`, `sizeEstimate` |

Ebből a `threadId` a lánc 2. lépését, a `fromEmail` az 1. és 3. lépését, az `id` pedig az idempotenciát hordozza. **Küldeni a szerződés nem tud** — a `draft` piszkozatot ír, és a kiadás az operátor kattintása a gmail saját lapján. A CRM ebben a fázisban nem is nyúl hozzá.

## File Structure

| Fájl | Felelőssége |
|---|---|
| `extensions/crm/src/mcp-bridge.mjs` | **bájtra azonos** másolat az `aisignal`-éból. Két rpc-metódus, ami a `tools` tömb fölé reflektál. |
| `extensions/crm/mcp/server.mjs` | a generikus stdio-shim; csak `EXTENSION_ID` és `SERVER_INFO` tér el a testvéreitől |
| `extensions/crm/src/matching.mjs` | **tiszta függvény**: kihez tartozik ez a levél. Nem ír, nem hálózik, nincs benne SQL. |
| `extensions/crm/src/sweep.mjs` | a szerződés → esemény út. Az egyetlen fájl, ami a szerződést hívja. |
| `extensions/crm/src/db.mjs` | +`sweep_state` tábla és a hozzá tartozó pár metódus |
| `extensions/crm/ui/ma.tsx` | a besorolatlan sor hozzárendelő gombja, kapcsolat-választóval |
| `extensions/crm/ui/ugyfel-lap.tsx` | idővonal-lapozás és teljes szöveg megnyitása |

A `matching.mjs` azért külön fájl és azért tiszta függvény, mert **ez a legkockázatosabb logika az egész rendszerben**: a hibája nem látszik. Egy rosszul besorolt levél működő rendszernek néz ki, csak rossz ügyfél idővonalára ír. Tiszta függvényként táblázatosan tesztelhető, adatbázis és hálózat nélkül.

```js
    /**
     * Hol tart a söprés. Egy sor forrásonként (`key`), mert a CRM-4 leiratai
     * és a naptár saját kurzort visznek majd.
     */
    getSweepState(key) {
      return S.get('SELECT * FROM ext_crm_sweep_state WHERE key = ?', [key]) || null
    },

    setSweepState(key, { cursor = '', lastSeenAt = '' } = {}) {
      S.exec(
        `INSERT INTO ext_crm_sweep_state (key, cursor, last_seen_at, updated_at)
         VALUES (?, ?, ?, ?)
         ON CONFLICT(key) DO UPDATE SET cursor = excluded.cursor,
           last_seen_at = excluded.last_seen_at, updated_at = excluded.updated_at`,
        [key, str(cursor), str(lastSeenAt), now()],
      )
      return S.get('SELECT * FROM ext_crm_sweep_state WHERE key = ?', [key])
    },
```

```js
     *
     * A lap ezt írja ki, nem hallgat: az operátort jobban szolgálja egy

    async mailboxHealth() {
```

```js
 * van. Ha ezekre tippelnénk, az első ilyen ügyfél magához szippantaná az
 * összes többi magánemailt.
 */
export const SOCIAL_DOMAINS = new Set([
  'gmail.com', 'googlemail.com', 'freemail.hu', 'citromail.hu', 'indamail.hu',
  't-online.hu', 'vipmail.hu', 'outlook.com', 'hotmail.com', 'live.com',
  'yahoo.com', 'yahoo.co.uk', 'icloud.com', 'me.com', 'proton.me', 'protonmail.com',
])

const domainOf = (address) => {
  const at = String(address || '').lastIndexOf('@')
  return at < 0 ? '' : String(address).slice(at + 1).trim().toLowerCase()
}

/**
 * Első találat nyer. A sorrend a spec 3.3-a, és a két „biztos" ág megelőzi a
 * „gyanú" ágat.
 */
export function matchMessage({ fromEmail, threadId }, lookups) {
  // 1. Pontos cím. A legerősebb jel: az operátor vette fel vagy erősítette meg.
  const contact = fromEmail ? lookups.contactByEmail(fromEmail) : null
  if (contact && contact.accountId) {
    return { kind: 'exact', accountId: contact.accountId, contactId: contact.id }
  }

  // 2. A szál. Ez fogja el a szál közbeni címváltást: ha ugyanabban a
  //    beszélgetésben már besoroltunk egy üzenetet, a folytatás oda tartozik,
  //    akkor is, ha a feladó közben magánemailre váltott.
  const threadAccount = threadId ? lookups.accountIdByThread(threadId) : null
  if (threadAccount) {
    return { kind: 'thread', accountId: threadAccount, contactId: contact ? contact.id : null }
  }

  // 3. Domain. Csak TIPP, és csak akkor, ha egyértelmű.
  const domain = domainOf(fromEmail)
  if (domain && !SOCIAL_DOMAINS.has(domain)) {
    const jeloltek = lookups.accountsByDomain(domain)
    // Két ügyfél ugyanazon a domainen nem tipp, hanem érme feldobás. Inkább
    // semmit, mint ötven százalékot.
    if (jeloltek.length === 1) return { kind: 'guess', guessAccountId: jeloltek[0] }
  }

  return { kind: 'none' }
}
```

```js
import { matchMessage } from './matching.mjs'

/**
 * A szerződéstől az eseményig. Az egyetlen fájl, ami a `mailbox` szerződést
 * hívja.
 *
 * IDEMPOTENS, ÉS EZ KÖVETELMÉNY, NEM KÉNYELEM. A `recordEvent` a
 * `(source_system, source_id)` unique indexre bízza a döntést, tehát ugyanaz a
 * levél kétszer behúzva egy sor marad. Ez teszi a söprést újrafuttathatóvá
 * anélkül, hogy bárkinek számon kellene tartania, meddig jutott.
 *
 * AMI NEM BIZTOS, AZ NEM KERÜL AZ IDŐVONALRA. A domain-tipp a besorolatlan
 * sorba megy `guess_account_id`-vel — egy kattintás az operátornak, és a
 * kattintás egyben megtanulja a címet (rpc `assignUnmatched`). Ha a tipp
 * automatikusan besorolna, a `noreply@`, a könyvelő és a külsős alvállalkozó
 * mind az ügyfél idővonalára kerülne, onnan az összefoglalójába.
 */
export function createSweep(state) {
  const repo = () => {
    if (!state.repo) throw new Error('crm_nincs_tar')
    return state.repo
  }

  const mailbox = () => {
    const handle = state.contracts ? state.contracts.get('gmail', 'mailbox', 1) : null
    if (!handle) throw new Error('crm_nincs_postafiok')
    return handle
  }

  return {
    /** Teszt-varrat: a szerződés-forrás cserélhető. Éles kódból ne olvasd. */
    __state: state,

    async runSweep({ labelIds, max = 50 } = {}) {
      const r = repo()
      const box = mailbox()
      const lookups = {
        contactByEmail: (a) => r.contactByEmail(a),
        accountIdByThread: (t) => r.accountIdByThread(t),
        accountsByDomain: (d) => r.accountsByDomain(d),
      }

      const lap = await box.list({ labelIds, max, cursor: r.getSweepState('gmail')?.cursor || undefined })
      let recorded = 0
      let unmatched = 0

      for (const id of lap.ids) {
        const msg = await box.get({ id })
        if (!msg) continue
        const talalat = matchMessage({ fromEmail: msg.fromEmail, threadId: msg.threadId }, lookups)

        if (talalat.kind === 'exact' || talalat.kind === 'thread') {
          const { created } = r.recordEvent({
            accountId: talalat.accountId,
            contactId: talalat.contactId || null,
            kind: 'email_in',
            occurredAt: msg.sentAt,
            title: msg.subject || '',
            excerpt: String(msg.text || '').slice(0, 200),
            sourceSystem: 'gmail',
            sourceId: msg.id,
            threadId: msg.threadId || '',
            body: msg.text || '',
          })
          if (created) recorded += 1
          continue
        }

        const { created } = r.recordUnmatched({
          sourceSystem: 'gmail',
          sourceId: msg.id,
          senderAddress: msg.fromEmail || '',
          senderName: msg.fromName || '',
          subject: msg.subject || '',
          excerpt: String(msg.text || '').slice(0, 200),
          receivedAt: msg.sentAt,
          guessAccountId: talalat.kind === 'guess' ? talalat.guessAccountId : null,
        })
        if (created) unmatched += 1
      }

      r.setSweepState('gmail', { cursor: lap.complete ? '' : (lap.nextCursor || ''), lastSeenAt: new Date().toISOString() })
      return { scanned: lap.ids.length, recorded, unmatched, complete: lap.complete, cursor: lap.nextCursor || '' }
    },
  }
}
```

## Önellenőrzés — a terv a spec ellen

**Spec-lefedettség.** A spec 12. fejezetének CRM-2 sora: „`consumes` a gmail szerződést, hozzárendelési lánc, besorolatlan sor és a tanulás." Rendre: Task 2 (`consumes`), Task 3 (lánc), Task 4 (besorolatlan sor feltöltése), Task 6 (tanulás). A spec 3.3 négy lépése mind a Task 3 táblázatos tesztjében szerepel.

**Amit a terv a specen felül vesz fel, és miért.** Az MCP-híd (Task 1) nincs a spec CRM-2 sorában — a spec a CRM-3-hoz sorolja. Előrehozzuk, mert a CRM-1 négy eszköze e nélkül **egyetlen ügynökhöz sem jut el** ebben a telepítésben (minden ügynök `claude-cli`-n fut), és mert a híd időközben szabványosított két-fájlos másolássá vált, amit egy parity-teszt őriz — nem az a hatszáz soros egyedi munka, aminek a CRM-1 tervezésekor látszott. A spec fázis-táblázatát ennek megfelelően frissíteni kell.

**Névegyezés.** A `matchMessage` `kind` értékei (`exact` | `thread` | `guess` | `none`) a Task 3 tesztjében és a Task 4 söprésében ugyanazok. A `recordEvent` új `threadId` argumentuma és az `ext_crm_event.thread_id` oszlop a Task 4 Step 1-ében együtt születik.

**Migráció.** A v2 migráció a `sweep_state` táblát ÉS az `ext_crm_event.thread_id` oszlopot is hozza. A v1-et nem írjuk át: élesben már lefutott.
